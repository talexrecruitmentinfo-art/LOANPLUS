# Feature-to-API audit

This matrix records the checked-in implementation as audited on 2026-10-18. An existing database model or screen is not evidence that a workflow is operational. “Unavailable” means the customer UI must not claim the operation succeeded.

| Feature and screen | API and access | Validation and persistence/state | Audit, errors, and tests | Current coverage / gap |
|---|---|---|---|---|
| Loan catalogue and customer application (`/loans`) | `GET /loans/products` is public; `POST /loans/applications`, `GET /loans/applications`, and `POST /loans/applications/:id/accept` require a customer session. | Server resolves the product by ID, checks account/product availability and configured amount bounds, normalizes and de-duplicates guarantor phones, requires accepted terms, and persists a draft with acceptance time and product-terms snapshot in `LoanApplication.applicationData`. Accepted pricing is used for the later Admin decision snapshot. Legacy applications without this snapshot are preserved but cannot be approved against mutable terms; staff review is required. | Idempotency keys and state guards; auth/audit log on offer acceptance; loan service unit/integration tests. | Catalogue-first selection, loading/empty/error/retry states, cost review and acceptance are implemented. Structured enforcement of arbitrary `eligibilityRules` is not implemented; browser viewport verification remains outstanding. |
| Processing-fee collection | `GET /payments/loan-processing-fee-quote`; authenticated `POST /payments/loan-processing-fee`; tokenized `POST /payments/mpesa/callback/:token`; authenticated `GET /payments`. | Fee amount and policy come from API; initiation requires accepted product snapshot, active customer, draft ownership/state, approved policy, KES clearing/revenue accounts, M-Pesa configuration, and idempotency. Pending provider results do not submit the application. Verified callback settlement, ledger posting and application submission are transactional. | Callback/provider-ID/amount/phone/receipt checks; duplicate callback protection; reconciliation tests and integration tests. | Source supports collection only. Deployment must provide approved policy, active `MPESA_CLEARING`, configured KES revenue account, callback URL and authorized Daraja credentials/live gate. Unresolved outcomes block new processing-fee attempts for the customer. |
| Wallet balance and activity | Authenticated `GET /wallet`, `GET /wallet/transactions`, and `GET /payments`. | Balance is derived from posted KES ledger entries. Payment and ledger reads are customer-scoped. | Ledger and payment tests. | Read-only. M-Pesa deposits, internal transfers and payout withdrawals have no customer write API and remain explicitly disabled; no balance is set by the frontend. |
| Customer authentication/profile/security | `/auth/register`, `/auth/login`, `/auth/me`, `/auth/logout`, password reset request/complete and password change. Customer-session protected where applicable. | Encrypted/hash-protected identity fields and expiring single-use reset-token records are present. | Auth audit and authentication/security tests. | No Admin password viewing or password-setting workflow is exposed. Customer personal-detail editing and verification review workflow are not implemented. |
| Referrals | Customer `GET /referrals/me`; Admin `GET /admin/referrals`. | Referral records and status are persisted. | Referral service tests. | Reward posting/configuration is not a live wallet workflow; qualifying activity must not be shown as a credited reward unless the ledger has posted it. |
| Customer support | Customer `GET/POST /support/tickets`; Admin `GET /admin/support/tickets` and `PATCH /admin/support/tickets/:id/reply`. | Persistent ticket, response and status records; server-side ownership checks. | Support integration tests. | Notification delivery depends on separately configured notification services. |
| Admin portal shell | Nested Admin layout and protected API routes; `/admin/login` remains outside the portal shell. | Shared sidebar and top bar link to the existing Admin routes; responsive drawer is scoped to Admin pages. | Superadmin API guards remain unchanged; web tests verify route coverage and scoped styles. | Admin-only responsive navigation and visible focus states are implemented. |
| Admin system health and incidents | Superadmin `GET /admin/system-health`, `POST /admin/system-health/check`, incident note and acknowledgement routes. | Manual checks probe API request handling, PostgreSQL via `SELECT 1` with a three-second timeout, configuration structure, reconciliation exceptions and accounting prerequisites. Component observations, fingerprint-deduplicated incidents, notes, recovery evidence and alert state are persisted when PostgreSQL is available. Failed email alerts have a five-minute retry cooldown and a three-attempt cap. | Superadmin guard, audited on-demand checks/notes/acknowledgements/recovery, alert delivery tests. M-Pesa and email providers are not contacted by the health check. | On-demand monitoring only; no scheduler/worker exists. M-Pesa/provider callback reachability, API error rates, callback processing health, job backlog and incident trends are not independently monitored. A database outage cannot persist its own incident or trigger an email alert. Configure email and review/apply the health, alert-retry, and audit-metadata migrations before relying on stored monitoring. |
| Admin customer management | Superadmin `GET /admin/customers`, `GET /admin/customers/:id`, `PATCH /admin/customers/:id/status`, `PATCH /admin/customers/:id/profile`, and throttled `POST /admin/customers/:id/password-reset`. | Server-side search and pagination. Profile endpoint changes display name only, requires a reason, and checks `updatedAt` to reject stale edits; email remains read-only because no verified-contact-change workflow exists. Status changes require a reason and revoke customer sessions. Admin reset reuses the existing hashed, expiring, single-use customer reset-token flow and sends only through configured Resend email. | `SuperadminSessionGuard`, request validation, optimistic update, transactional before/after profile/status audit details, reset initiation/delivery audit outcomes, and unit tests. Neither password nor token is returned. Failed email invalidates the newly created token. | Name edit, account suspend/reactivate and secure Admin reset request are implemented and unit-tested. Email/phone editing, verification decisions, dedicated ledger detail, and Admin identity verification remain unavailable. Delivery depends on Resend configuration; end-to-end reset completion via email was not browser-tested. |
| Admin payment monitoring | Superadmin paginated `GET /admin/payments`; reconciliation queue and actions at `/admin/payment-reconciliation`. | Server-side search, status/type/date filters and stable pagination; list selects safe provider identifiers and callback summaries only. Historical activation records are labelled separately; FAILED / `MPESA_RESULT_4999` remains unresolved. | Admin guards, controller/service tests, existing idempotency and reconciliation tests. No raw payloads are exposed. | Compact responsive table and expandable references/callback details are implemented. CSV export and extended provider status-change timeline remain unavailable. |
| Website management | Public `GET /platform/website`; Superadmin `GET /admin/website`, `GET /admin/website/history`, `PUT /admin/website/draft`, `POST /admin/website/publish`, `DELETE /admin/website/draft`, `POST /admin/website/assets`. | Drafts/publications are versioned in `WebsiteContentRevision`; public endpoint returns published content only. Uploads are restricted to supported image types/size and signature checks. | Website service/content tests; Admin authorization. | Draft persistence, preview/publication and history are present. A full real-browser publish/rollback test was not run in this environment. |
| Admin settings and accounting | Superadmin loan-product and processing-fee settings under `/admin/loans`; ledger account listing/creation at `/admin/ledger/accounts`; currency, PWA and reconciliation controls under `/admin/settings/platform`. | Server validates account type/currency and records system settings/account rows. Processing-fee configuration exposes policy readiness and accounting blockers read-only; external approval is not self-certifiable. | Admin audit writes and platform-settings tests. | Existing contracts cover only these settings. Full security/session/notification/payout/maintenance and account-deactivation controls are not present. |
| Admin audit | Superadmin `GET /admin/audit` with server-side search, actor/action/resource/outcome/date filters and pagination. | `AdminAuditLog` has optional safe JSON details for selected before/after changes; normal API operations do not expose update/delete routes. | API query validation and pagination tests; UI provides filters, loading/error/empty states and expandable safe details. | Profile and account-state before/after details are available. Existing reconciliation, website, settings, and security audit writes remain uneven and do not all have complete before/after snapshots. |
| Loan disbursement and repayment | Superadmin loan review and manual disbursement confirmation under `/admin/loans`; customer reads application/loan status. | Decision snapshots and disbursement ledger entries are persisted and guarded; no approved loan is spendable before confirmed disbursement. | Loan and ledger integration tests. | Authorized manual disbursement is supported; customer repayment collection and automated payout integration are not implemented. |
| PWA installation | Public `GET /platform/pwa/eligibility`; Superadmin setting at `/admin/settings/platform/pwa-installation`. | Eligibility is read from persisted platform settings. | Platform-settings tests. | Customer install entry is in Profile and does not uninstall an existing device installation. |

## High-priority audit checklist

- [x] Existing customer/Admin/API modules, Prisma schema/migrations, environment gates and tests inspected; reference image viewed.
- [x] Existing baseline tests run before edits.
- [x] Reused existing loan, M-Pesa, ledger, reconciliation, website, support, referral, settings and audit APIs; no second backend or migration added.
- [x] Product-first application, server-recorded terms acceptance, immutable accepted-terms snapshot, visible payment blocking, five-item navigation and compact transaction details updated.
- [ ] Implement and test wallet deposit, internal transfer and authorized withdrawal APIs before enabling those actions.
- [x] Add Admin customer detail history, audited suspend/reactivate with session revocation, and paginated customer/payment search filters.
- [ ] Finish profile edits, secure Admin password-reset initiation, identity-verification review, ledger detail, scheduled health checks/provider and callback monitoring, configurable thresholds/trends, database-outage alert routing, complete settings/audit coverage, and requested browser/persistence verification.
- [ ] Run isolated-database integration tests, staging provider verification, and responsive browser checks before production.

The baseline/full repository tests do not connect to production. Database-backed suites can be skipped when `DATABASE_URL` is unavailable; no live payment, production database, payout, or browser session has been exercised as part of this audit.
